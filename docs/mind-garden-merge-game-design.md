# 心象花园 Merge-3 养成游戏策划稿

版本：`v0.1`  
状态：讨论稿，尚未进入游戏实现  
产品：心象仪 / 心象花园

## 1. 一句话定义

用户通过每日写日记获得心种，在花园中将三株相同种类、相同等级的植物融合成一株更高等级的植物；植物持续产生游戏货币，逐步点亮植物图谱，并为未来的装饰、道具和 3D 花园提供长期成长基础。

## 2. 核心目标

心象花园不是一个额外要求用户完成的任务系统，而是日记习惯产生的可见成果。

核心体验应满足以下原则：

1. 日记是唯一必要入口。用户不需要为了游戏额外填表。
2. 低落日记与快乐日记获得相同的基础奖励，不对真实情绪进行奖惩。
3. 植物不再与某一天一一对应，日记只负责提供心种和环境变化。
4. 游戏结果优先于数据面板。养成页主要展示花园、融合和图谱，不堆统计卡。
5. 游戏可以长期扩展，但 MVP 的规则必须简单、可解释、可离线运行。
6. 游戏状态和日记状态分层保存，避免修改日记时破坏已经完成的融合结果。

## 3. 核心循环

```text
写一篇日记
    ↓
领取 1 个心种匣
    ↓
获得 1 株一级植物
    ↓
收集三株同种、同级植物
    ↓
融合为一株更高等级植物
    ↓
更高等级植物持续产生心光
    ↓
点亮图谱 / 扩建花园 / 购买装饰与道具
    ↓
回到下一次日记打卡
```

单次游戏操作应控制在 30 秒到 2 分钟。用户可以只写日记并离开，也可以在有兴趣时整理花园和完成融合。

## 4. 日记与游戏的关系

### 4.1 每日奖励

- 每个自然日首次保存有效日记时，生成 1 个未开启的 `心种匣`。
- 同一天反复修改日记只更新心象分析，不重复发放奖励。
- 奖励使用 `entryId + dateKey` 作为幂等键，跨端同步后也只能领取一次。
- 日记删除后不自动回收已经领取或融合的植物，避免用户因为整理历史记录而失去游戏成果。
- 空日记和只有附件、没有正文的记录是否发放心种，MVP 建议仍沿用当前保存规则，但至少需要一段非空正文才计为游戏打卡。

### 4.2 心象分的作用

心象分不直接决定奖励数量、植物价值或赚钱速度。它只影响以下软性内容：

- 当日花园天气、天空颜色和环境音。
- 心种匣中不同植物家族的概率权重。
- 图谱中的“发现记录”和植物背景故事。
- 未来装饰推荐，例如雨天更容易推荐灯、伞、苔藓等主题，但价格不因心情变化。

这样既能保留心象仪“从日记计算一天状态”的特色，又不会让低心情变成游戏惩罚。

### 4.3 植物与日期解耦

- 日记不再永久绑定某一株植物。
- 植物可以被移动、融合、收藏或放入仓库。
- 植物可保留 `sourceEntryId` 作为可选来源记录，但来源只用于回看，不参与融合规则。
- 融合后的植物记录三个来源植物 ID，而不是只保留某一天。

## 5. 融合规则

### 5.1 基础规则

- 三株 `植物家族相同 + 等级相同` 的植物可以融合。
- 融合消耗三株原植物，生成一株同家族、等级加一的新植物。
- 新植物出现在用户最后拖入的格子，其余两个格子变为空位。
- 融合必须是数据库事务：消费三株和生成一株要么全部成功，要么全部失败。
- 每株植物拥有永久唯一 ID，不能依靠格子位置判断是否已消费。

### 5.2 是否要求相邻

MVP 推荐采用“全棋盘可融合”，不强制三株相邻。

原因：

- 这是日记附属养成，不应因为格子排列制造过多挫败感。
- 手机端拖动精度有限，全棋盘识别更轻松。
- 用户拖动一株到同类植物上后，系统可自动高亮第三株并完成吸收动画。
- 后续若需要更强策略性，可以增加一个独立的挑战花圃，在挑战模式中要求相邻融合。

### 5.3 等级与节奏

首版建议每个植物家族提供 5 个等级：

| 等级 | 名称示例 | 累计需要一级植物 | 基础产出建议 |
| --- | --- | ---: | ---: |
| 1 | 心芽 | 1 | 1 心光/小时 |
| 2 | 幼苗 | 3 | 4 心光/小时 |
| 3 | 花株 | 9 | 14 心光/小时 |
| 4 | 盛放 | 27 | 45 心光/小时 |
| 5 | 灵植 | 81 | 140 心光/小时 |

融合后的产出略高于三株原植物之和，让融合有明确价值，但不产生失控的指数膨胀。

## 6. 植物家族与图谱

MVP 建议保留四个基础家族，但不再和某一天固定绑定：

| 家族 | 视觉方向 | 心象概率倾向 | 说明 |
| --- | --- | --- | --- |
| 月影系 | 靛紫、蕨叶、夜光 | 低能承压时略提高 | 安静、收纳压力，不代表低价值 |
| 风铃系 | 珊瑚、铃形花、风动 | 高能紧绷时略提高 | 有张力、动态明显 |
| 晨露系 | 青绿、芽苞、水珠 | 低能修复时略提高 | 柔和、恢复感强 |
| 向阳系 | 金黄、宽叶、日光 | 高能舒展时略提高 | 明亮、开放感强 |

所有心种匣都应有机会开出四个家族。心象只调整概率，不做绝对映射，也不改变植物产出价值。

图谱采用 `家族 × 等级` 的节点结构：

- 未发现节点显示剪影。
- 首次生成或融合到该节点时点亮图鉴。
- 节点展示像素立绘、名称、首次发现日期和最高持有数量。
- 点击已发现节点可查看来源日记，但不展示过度敏感的正文摘要。
- 后续版本可以在五级植物之间加入跨家族培育，形成图谱分支，而不是无限增加线性等级。

## 7. 花园棋盘

### 7.1 MVP 布局

- 默认使用 `6 × 6` 花圃，共 36 个格子。
- 初始开放 24 个格子，其余格子可在后续版本用心光解锁。
- 一级植物从心种匣进入待放置区，不强制立即占用棋盘。
- 提供一个小型仓库，避免棋盘满后阻塞日记奖励。
- 棋盘满时仍能领取心种匣，但不能开启，用户不会丢失奖励。

### 7.2 交互

- 点击植物：打开轻量信息条，显示名称、等级、产出和来源入口。
- 拖动植物：移动格子；拖到同种同级植物上时预览融合。
- 长按植物：进入批量整理模式。
- 双击可融合植物：自动选择另外两株并询问一次，之后可在设置中关闭确认。
- 完成融合时使用短促的吸收、闪光和生长动画，时长控制在 600 到 900 毫秒。
- 支持键盘方向键移动焦点、空格选中、Enter 融合，确保桌面端完整可操作。

## 8. 心光与离线产出

### 8.1 货币

首版货币暂定名为 `心光`。

- 每株已放置植物按等级持续产生心光。
- 仓库中的植物不产出，鼓励用户展示自己的成果。
- 心光只存在于游戏系统，不反向影响心象分和日记分析。
- 不接入真实货币，不设计付费点。

### 8.2 离线结算

- 记录 `lastCollectedAt`，打开花园时按已放置植物的产出率结算。
- MVP 离线收益上限建议为 12 小时，避免无限累积导致经济失控。
- 结算应使用服务层纯函数计算，桌面、Android 和 Web 得到一致结果。
- 修改系统时间不能产生负收益；发现时间倒退时沿用上次可信时间。
- 收取心光是显式操作，画面上直接从植物汇入顶部货币栏，提供成果感。

### 8.3 后续消耗方向

商店与道具不进入第一版实现，但数据结构需要预留：

- 花圃格子扩建。
- 地面、围栏、天空、天气和背景音乐皮肤。
- 纯装饰物：长椅、灯、石头、水池、路牌。
- 仓库扩容。
- 一次性整理工具，例如自动归拢同类植物。
- 稀有心种匣和跨家族培育材料。

道具不应购买“更高心情分”或改变日记算法，避免把情绪健康游戏化为数值竞争。

## 9. 养成页信息架构

用户已经明确不希望养成页堆叠大量统计，建议采用以下结构：

```text
顶部轻量 HUD
心光余额 · 待收收益 · 心种匣数量

主要区域
可交互花园棋盘，占据首屏绝大部分

选中植物时
底部出现一条植物信息栏

底部工具栏
心种匣 · 图谱 · 仓库 · 商店（后续）
```

不在主界面常驻展示：平均心象分、累计 Todo、算法置信度、长篇规则说明、完整成就列表。它们应分别留在回顾页、设置页或二级弹窗中。

## 10. 视觉与声音方向

### 10.1 MVP 推荐风格

- 安静、克制的 16-bit 像素花园，不采用高饱和手游大厅风格。
- 植物轮廓清楚，颜色以绿色为环境基底，黄色用于可收取、可融合和新发现反馈。
- 像素画布保持固定逻辑分辨率，使用整数倍缩放和 `image-rendering: pixelated`。
- 天气、光照和微风提供慢动画；融合和收取提供短动画。
- 移动端优先保证触控目标、文字清晰度和不遮挡底部导航。

### 10.2 声音与触觉

- 默认关闭或低音量，遵循系统静音设置。
- 收取心光：轻微玻璃或木琴音。
- 融合：三段短音阶和一次轻触觉反馈。
- 新图谱节点：比普通融合更明显，但不使用持续弹窗。

## 11. 技术架构建议

### 11.1 游戏规则与渲染分离

游戏不应把规则写在 React 组件或图形引擎中。建议分成三层：

```text
GardenGameCore
纯 TypeScript：奖励、融合、产出、图谱、幂等与校验
        ↓
GardenGameStore
SQLite：植物、棋盘、货币、事件、库存和同步
        ↓
GardenRenderer
PixiJS 像素场景；未来可替换为 Three.js / Babylon.js
```

这样未来从 2D 换到 3D 时，只替换渲染层和资源，不重写融合、货币和同步规则。

### 11.2 引擎选择

MVP 推荐 `PixiJS 8`，不推荐此阶段直接使用 Phaser：

- PixiJS 更适合以棋盘、精灵、粒子和拖拽为主的 2D 场景。
- 当前不需要 Phaser 内置的物理、碰撞和完整场景系统，额外体积收益有限。
- PixiJS 可与 React 外壳共存，日记、设置和弹窗继续使用现有组件。
- 像素精灵、合批和移动端 WebGL 性能更可控。

未来 3D 推荐 `Three.js + React Three Fiber` 或 Babylon.js。3D 版本应实现同一个 `GardenRenderer` 输入协议，继续消费游戏核心输出的棋盘和植物实例。

### 11.3 建议数据表

```text
garden_profiles
- id
- coins
- last_collected_at
- board_revision
- created_at / updated_at / sync_state

garden_plants
- id
- family
- tier
- board_slot
- source_entry_id
- created_from_merge_id
- created_at / updated_at / sync_state

garden_rewards
- id
- reward_key            # entryId + dateKey，唯一
- entry_id
- date_key
- reward_type
- claimed_at
- payload_json
- sync_state

garden_merges
- id
- consumed_plant_ids_json
- result_plant_id
- created_at
- device_id
- sync_state

garden_inventory
- id
- item_type
- item_key
- quantity
- updated_at / sync_state
```

数据库迁移必须同时更新 `server/local-api.mjs` 和 `src/lib/native-db.ts`，并遵循“建表 -> 补列 -> 建索引 -> 更新 user_version”的现有迁移顺序。

### 11.4 事务与校验

- 服务端或本地原生层必须重新校验三株植物是否存在、未被消费、家族一致、等级一致。
- 客户端传入的产出值、融合结果等级和货币金额不能直接信任。
- 融合事务内同时删除或标记三株原植物、创建结果植物、写入融合事件和更新图谱。
- 收取离线收益时使用数据库事务更新余额和 `lastCollectedAt`。
- 所有奖励和合并事件都有唯一幂等键，避免按钮连点或网络重试重复结算。

## 12. 多端同步策略

当前 WebDAV 快照同步适合个人数据，但游戏合并会消费具体植物，简单的最后写入覆盖可能造成重复或丢失。

MVP 建议：

1. 游戏状态继续本地优先保存到 SQLite。
2. 快照中包含游戏表和 `boardRevision`。
3. 进入花园前若已配置 WebDAV，先尝试同步；离开花园后再上传一次。
4. 两个设备同时修改同一版棋盘时，不自动静默合并，保留两份快照并提示选择。
5. 日记奖励通过唯一 `rewardKey` 去重，即使棋盘冲突也不会重复发放心种。

后续若要支持真正的跨端并发，需要按事件同步：奖励事件、移动事件、融合事件和收取事件分别拥有全局唯一 ID，并通过确定性顺序重放。这个能力不应塞进第一版。

## 13. MVP 范围

### 13.1 第一版必须完成

- 6 × 6 花园棋盘和待放置区。
- 四个植物家族，每个家族五个等级。
- 每日日记生成一个幂等心种匣。
- 开启心种匣并放置一级植物。
- 拖动、移动和三合一融合。
- 植物持续产出心光，支持 12 小时离线结算。
- 轻量顶部 HUD、植物详情条、图谱和仓库入口。
- 图谱节点解锁。
- SQLite 本地存档、API 鉴权、原子事务和隔离测试。
- 桌面和移动端键盘/触控可操作。

### 13.2 第一版明确不做

- 3D 场景。
- 商店、付费、广告或真实货币。
- 跨家族培育和稀有度系统。
- 好友、排行、分享或社交。
- 复杂任务、赛季和每日签到弹窗。
- 多设备并发事件合并。
- 用心情分决定奖励多少。

## 14. 后续阶段

### 阶段 2：经济与装饰

- 商店、装饰、棋盘扩建、仓库扩容。
- 稀有心种匣和自动整理道具。
- 更多图谱分支和环境主题。

### 阶段 3：更丰富的互动

- 植物摇摆、天气粒子、昼夜切换和环境音。
- 小型访客、昆虫或花园事件，但不引入强制任务。
- Todo 完成可提供少量浇水能量，不影响日记基础奖励。

### 阶段 4：3D 花园

- 用 Three.js / React Three Fiber 或 Babylon.js 实现新的渲染适配器。
- 复用现有棋盘、植物实例、融合、货币和图谱数据。
- 2D 像素模式继续保留，兼容低性能设备和偏好选择。

## 15. 验收标准

游戏第一版只有在以下条件同时满足时才算完成：

1. 同一天编辑日记十次，只能得到一个奖励。
2. 三株不满足条件的植物无法融合，且数据库不产生半成品。
3. 三株满足条件的植物融合后只生成一株结果植物。
4. 关闭应用再打开，棋盘、货币、图谱和仓库完全恢复。
5. 离线收益在桌面、Android 和 Web 计算一致。
6. 低心象分和高心象分获得相同基础心种数量。
7. 真库测试不写入样例数据，自动化测试只使用随机端口和临时数据库。
8. 390px 手机宽度没有横向溢出，底部导航不遮挡棋盘关键操作。
9. 键盘可以完成选中、移动、融合、打开图谱和关闭弹窗。
10. 游戏核心测试不依赖 PixiJS，换渲染器后规则测试仍可全部运行。

## 16. 实现前待确认项

以下为本策划稿的推荐默认值，进入编码前应由产品侧确认：

| 决策 | 推荐值 | 可选方案 |
| --- | --- | --- |
| 融合距离 | 全棋盘三株可融合 | 必须相邻 |
| 棋盘尺寸 | 6 × 6，初始开放 24 格 | 5 × 5 或全开放 |
| 植物家族 | 4 个 | 3 个或 5 个 |
| 首版等级 | 每家族 5 级 | 6 级 |
| 每日日记奖励 | 1 个心种匣 | 固定 2 个 |
| 离线收益上限 | 12 小时 | 8 小时或 24 小时 |
| 游戏货币名 | 心光 | 露珠、花息 |
| 2D 引擎 | PixiJS 8 | Phaser、自研 Canvas |
| 视觉风格 | 克制的 16-bit 像素花园 | 手绘 2D |

在这些项目确认前，不新增游戏数据库表、不安装图形引擎依赖，也不改写真实用户数据。
