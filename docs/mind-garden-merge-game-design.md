# 心象森林像素养成游戏策划稿

版本：`v0.2`  
状态：讨论稿  
产品：心象仪 / 游戏页

## 1. 当前方向

我们先做一个像素风格的养成游戏，不急着上 3D 引擎。

游戏应该像一个安静、有品味的 RPGMaker 小场景：玩家进入后看到的是一个完整的游戏画面，而不是统计页面。日记、心象分和 Todo 完成情况作为底层输入，转化成天气、植物、生长、经济和后续场景进度。

核心感受：

- 每天记录不是为了填表，而是在世界里留下东西。
- 低落、高压、平稳、舒展都能产生内容，不把情绪做成奖惩。
- 页面直接展示成果，少放解释、少放统计、少放大段提示。
- 后续可以不断添加场景，但规则核心要稳定。

## 2. 游戏页面外壳

### 2.1 沉浸式游戏页

进入游戏页面后，常规 App 外壳需要让位给游戏本体。

游戏页只保留导航入口：

- 保留当前底部导航栏。
- 不保留现有动态背景。
- 不保留顶部设置按钮。
- 不保留顶部同步按钮。
- 不在游戏画面上堆统计卡、同步状态、系统说明。

桌面端后续需要单独确认：如果继续保留左侧导航，它只能作为进入游戏的外部入口；游戏画面本身仍按沉浸式画布设计，不使用普通内容页布局。

### 2.2 游戏内 HUD

游戏内部只保留真正有用的轻量信息：

```text
右上角：成就入口
左上角：货币 / 当前天气 / 当日可领取内容
底部：当前 App 导航栏
点击对象后：底部或侧边浮出对象信息
```

不常驻展示：

- 平均心象分
- 算法置信度
- 累计 Todo 数
- 大段规则解释
- “你应该怎么做”的教学文案

## 3. 美术方向

### 3.1 基础风格

- 16-bit / RPGMaker 风格像素场景。
- 地块、植物、房屋、人物都使用 tile + sprite 体系。
- 色彩以绿色、土黄、暖光为基础，避免手游大厅式高饱和。
- 重要交互用黄色/浅绿色提示。
- 所有像素资源使用整数倍缩放，CSS 层保持 `image-rendering: pixelated`。

### 3.2 场景表达

游戏不是数据仪表盘，它应该像一个可以停留的地方。

第一阶段可以用 2D 像素画布实现：

- 固定俯视或 3/4 视角。
- 地面由 tile 拼接。
- 植物是可点击、可拖动、可合成的 sprite。
- 天气、光照、云、雨、雾用轻量动画表达。

后续如果要做 3D，应该只替换渲染层，不重写规则层。

## 4. 多场景结构

游戏支持多个场景，每个场景用同一套数据输入，但有不同玩法。

```text
日记 / 心象分 / Todo 完成
        ↓
每日结算
        ↓
场景 1：心象森林
        ↓
解锁资源与长期收益
        ↓
场景 2：森林建房
        ↓
更多生活空间与装饰
        ↓
后续场景
```

第一版只做第一个场景：心象森林。  
第二个场景先进入策划，不急着实现。

## 5. 场景一：心象森林

### 5.1 一句话定义

用户每天写日记和完成 Todo，会在像素森林中获得新的自然内容；三株相同植物可以融合成更高阶植物，长期形成一片森林，并持续产生游戏货币。

### 5.2 每日输入

每天结算时读取三类数据：

| 输入 | 作用 |
| --- | --- |
| 前一天心象分 / 心象象限 | 决定今天进入森林时的天气与氛围 |
| 当天日记心象数据 | 决定新增植物的概率、颜色或特殊表现 |
| 当天完成 Todo 数 | 决定额外资源、行动力、掉落或施工潜力 |

心象分不直接决定“奖励多还是少”。它主要改变天气、植物倾向和视觉气质。

### 5.3 天气系统

天气由前一天的心情状态决定。这样打开游戏时，会有一种“昨天留下了今天的天空”的感觉。

示例映射：

| 前一天状态 | 今日天气 | 视觉 |
| --- | --- | --- |
| 低能承压 | 雾 / 小雨 | 深绿、蓝灰、低云 |
| 低能修复 | 晨露 / 阴晴 | 浅绿、水珠、柔光 |
| 高能紧绷 | 风 / 雷云边缘 | 快速云影、风线、摇摆 |
| 高能舒展 | 晴 / 金色光 | 暖光、明亮树冠 |
| 平稳 | 多云 | 中性光照 |

天气只影响场景表现和轻微概率，不惩罚用户。

### 5.4 植物生成

每天打卡后获得一个植物或心种。

植物生成参考：

- 日记心象象限决定植物家族概率。
- 心象分决定颜色明度、天气适配和少量变体。
- 完成 Todo 数可以增加额外掉落概率或行动力。
- 同一天反复编辑日记不重复发放植物。

植物不再和日期永久一一绑定。日期只作为来源记录，植物可以移动、融合、出售或进入仓库。

### 5.5 合成体系

为避免植物越来越多导致画面放不下，采用三合一融合。

基础规则：

- 三株相同植物可以融合。
- 融合后生成一株更高阶、更大的植物。
- 被融合的三株植物消失。
- 新植物拥有更高经济收益。
- 合成结果进入图谱。

第一版可以采用这条成长链：

```text
藻类
  ↓ 三合一
蕨类
  ↓ 三合一
灌木
  ↓ 三合一
乔木
  ↓ 三合一
巨木 / 森林核心
```

每一层都应该有明显视觉差异，而不是只把 sprite 放大。

### 5.6 经济收益

植物可以产生游戏货币，暂定名仍为 `心光`。

收益原则：

- 高阶植物收益高于低阶植物。
- 合成收益应略高于三株原植物总和，让融合有明确价值。
- 仓库植物默认不产出，摆在森林中的植物才产出。
- 不接入真实货币，不设计付费点。

示例：

| 阶段 | 名称 | 需要基础植物数 | 产出 |
| --- | --- | ---: | ---: |
| 1 | 藻类 | 1 | 1 心光/小时 |
| 2 | 蕨类 | 3 | 4 心光/小时 |
| 3 | 灌木 | 9 | 14 心光/小时 |
| 4 | 乔木 | 27 | 45 心光/小时 |
| 5 | 巨木 | 81 | 140 心光/小时 |

数值只是讨论默认值，后续实现前再调。

### 5.7 图谱

图谱记录玩家已经解锁过的自然内容。

图谱结构：

```text
植物家族
  ├─ 藻类
  ├─ 蕨类
  ├─ 灌木
  ├─ 乔木
  └─ 巨木
```

图谱只展示成果：

- 像素立绘
- 名称
- 等级
- 首次发现日期
- 当前持有数量
- 产出

不展示长篇算法说明。

## 6. 场景二：森林建房

### 6.1 解锁条件

当森林达到一定成熟度后，解锁建房场景。

可能条件：

- 拥有若干乔木。
- 连续打卡达到一定天数。
- 森林总产出达到一定门槛。
- 图谱解锁到某个阶段。

### 6.2 一句话定义

用户利用森林产生的资源建造一座像素小屋。每天的心情参数和 Todo 完成情况决定当天施工进度，房子从地基、一楼、二楼到屋顶逐步完成。

### 6.3 建造阶段

```text
清理地面
  ↓
地基
  ↓
一楼
  ↓
二楼
  ↓
屋顶
  ↓
室内布置
```

示例数值：

| 阶段 | 需要积分 | 预期耗时 |
| --- | ---: | --- |
| 地基 | 1000 | 约 10-14 天 |
| 一楼 | 1600 | 约 16-24 天 |
| 二楼 | 2200 | 约 22-32 天 |
| 屋顶 | 1200 | 约 12-18 天 |

每天最多获得 100 施工积分。  
这个上限可以让进度稳定，不至于一天冲完。

### 6.4 每日施工积分

施工积分由当天数据推导。

示例公式：

```text
基础施工 40
+ 日记打卡 20
+ Todo 完成数 × 8，上限 24
+ 心象稳定度 / 修复度加成，上限 16
= 当日施工积分，上限 100
```

注意：低心情不应该归零。低落时也可以获得基础施工，只是当天表现可能是“慢慢铺地基”“整理木材”。

### 6.5 建房与森林的关系

森林不是独立玩法，它为建房提供材料和经济基础。

可能关系：

- 乔木产出木材。
- 心光购买建筑装饰。
- 成熟森林解锁不同房屋外观。
- 特殊天气影响当天施工动画。

## 7. 成就系统

成就入口固定在游戏界面右上角。

成就不应该霸占主界面，只在达成时出现短反馈。

首批成就方向：

- 第一次打卡生成植物。
- 第一次三合一融合。
- 第一株乔木。
- 第一片森林。
- 第一次收取心光。
- 解锁建房场景。
- 完成地基。
- 完成一楼。
- 连续打卡 7 / 14 / 30 天。

成就界面可以作为图谱以外的长期目标，但不做强制任务列表。

## 8. 数据与安全原则

### 8.1 不污染原始数据

游戏只能读取日记、心象分和 Todo 完成情况作为输入。

不能：

- 为了测试往真实 Todo 写内容。
- 删除用户日记或 Todo。
- 因游戏回滚修改原始日记。
- 把游戏存档和原始记录混在一张表里。

### 8.2 游戏状态单独保存

游戏需要独立存储：

- 植物实例
- 合成记录
- 图谱解锁
- 货币
- 场景解锁
- 建房进度
- 成就状态

每日奖励必须幂等：

```text
rewardKey = dateKey + entryId + rewardType
```

同一天改十次日记，也只能得到一次基础奖励。

### 8.3 规则层与渲染层分离

为了后续从像素 2D 扩展到 3D，游戏应该拆成：

```text
GameCore
  计算奖励、天气、融合、收益、建造进度

GameStore
  SQLite 存植物、货币、成就、场景进度

GameRenderer
  第一版为像素 2D，后续可替换为 3D
```

React 负责页面外壳和弹窗，游戏画布负责场景表现。

## 9. 实现顺序建议

### 阶段 0：策划确认

- 确认游戏页只保留底部导航的沉浸式外壳。
- 确认第一场景名称。
- 确认货币名。
- 确认植物合成链。
- 确认天气映射。
- 确认建房是否作为第二场景。

### 阶段 1：游戏页面外壳

- 隐藏普通 App 背景。
- 隐藏顶部设置与同步。
- 保留底部导航。
- 做一个空的像素画布容器。
- 右上角放成就入口。

### 阶段 2：心象森林 MVP

- 像素地块。
- 初始植物实例。
- 天气表现。
- 三合一融合。
- 心光产出。
- 图谱入口。

### 阶段 3：经济与仓库

- 仓库。
- 离线收益。
- 森林容量控制。
- 基础商店。

### 阶段 4：建房场景

- 解锁建房。
- 地基进度。
- 每日施工结算。
- 房屋阶段动画。

## 10. 待确认问题

1. 游戏页在桌面端是否也完全使用底部导航，还是保留左侧导航作为外部入口？
2. 第一场景最终叫“心象森林”还是继续叫“心象花园”？
3. 货币名用“心光”还是换成“露珠 / 木息 / 星屑”？
4. 植物成长链是否固定为“藻类 → 蕨类 → 灌木 → 乔木 → 巨木”？
5. 每天是必定给一株植物，还是给一个心种匣让用户打开？
6. Todo 完成数更适合影响森林掉落，还是影响第二场景施工进度？
7. 建房的第一版是否只做地基，等森林 MVP 稳定后再扩展？
8. 是否需要一个小角色在场景里走动，增强 RPGMaker 感？

## 11. 暂不实现

在这份策划确认前，暂不做以下事情：

- 不安装 PixiJS / Phaser / Three.js。
- 不新增游戏数据库表。
- 不改写真实日记或 Todo 数据。
- 不做复杂经济系统。
- 不做 3D。
- 不做付费、排行、社交。
